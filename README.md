# Техническое задание

## Название проекта

**Universal Multi-Source Parser Engine**

---

# Цель проекта

Разработать высокопроизводительный движок на Go для работы с большим количеством однотипных источников данных.

Движок должен:

* периодически выполнять REST-запросы к каждому источнику;
* анализировать полученные данные;
* автоматически создавать и удалять WebSocket-подключения;
* поддерживать тысячи одновременных WebSocket-соединений;
* использовать пул HTTP- и WebSocket-прокси;
* легко масштабироваться путем добавления новых источников без изменения существующей архитектуры.

---

# Основные требования

## Производительность

Поддержка:

* десятков источников;
* нескольких тысяч WebSocket-соединений;
* нескольких сотен прокси;
* непрерывной работы 24/7.

---

## Масштабируемость

Добавление нового источника должно требовать создания только новой папки.

Например:

```text
exchange/
    bybit/

exchange/
    okx/

exchange/
    kucoin/
```

Без изменения Engine.

---

## Независимость источников

Каждый источник полностью инкапсулирует:

* REST;
* WebSocket;
* парсинг ответов;
* переподключение;
* heartbeat;
* управление собственными соединениями.

Engine ничего не знает о внутреннем устройстве источников.

# Назначение папок

## cmd

Точка входа.

Только запуск приложения.

Никакой бизнес-логики.

---

## core

Общие компоненты.

### config

Загрузка конфигурации.

### logger

Единый логгер проекта.

### domain

Общие структуры проекта.

Например:

```go
Symbol

Ticker

OrderBook

Trade

Instrument
```

Они не принадлежат конкретной бирже.

---

## engine

Главный координатор системы.

Отвечает за:

* запуск приложения;
* расписание;
* вызов обновления источников.

Engine **не знает**, как работает REST или WebSocket.

---

## exchange

Каждая биржа представляет собой самостоятельный модуль.

Внутри содержится абсолютно вся логика работы именно этой биржи.

---

## proxy

Управление всеми прокси.

---

# Ответственность Engine

Engine отвечает только за жизненный цикл приложения.

Пример работы:

```text
запуск

↓

создать источники

↓

каждые 60 секунд

↓

обновить каждый источник
```

Engine не занимается:

* websocket;
* json;
* reconnect;
* heartbeat;
* proxy.

---

# Интерфейс Exchange

Каждый источник обязан реализовывать один интерфейс.

```go
type Exchange interface {

    Name() string

    Sync(ctx context.Context) error
}
```

Engine работает исключительно через этот интерфейс.

---

# Ответственность Exchange

Каждая биржа самостоятельно выполняет:

```
REST

↓

парсинг ответа

↓

анализ изменений

↓

создание новых websocket

↓

закрытие старых websocket

↓

обновление внутренних данных
```

Никакая другая часть проекта не вмешивается в этот процесс.

---

# REST

REST отвечает только за получение информации.

Например:

```
получить список инструментов

получить рынки

получить настройки
```

REST ничего не знает о websocket.

---

# WebSocket

Один объект Connection соответствует одному websocket.

Connection умеет:

```
Connect()

Read()

Write()

Ping()

Reconnect()

Close()
```

Connection не знает, что существуют другие соединения.

---

# ConnectionManager

Каждая биржа имеет собственный ConnectionManager.

Он отвечает за:

* хранение соединений;
* создание новых;
* закрытие старых;
* переподключение;
* поиск соединения;
* контроль количества активных websocket.

Например:

```
BTC

↓

Connection

ETH

↓

Connection

DOGE

↓

Connection
```

---

# ProxyManager

Все прокси находятся в одном месте.

ProxyManager отвечает за:

* выдачу прокси;
* освобождение прокси;
* подсчет количества соединений;
* выбор наиболее свободной прокси.

---

# Алгоритм выбора прокси

Каждая прокси содержит счетчик активных websocket.

Например

```
Proxy1

12 соединений

Proxy2

34 соединения

Proxy3

8 соединений
```

При создании нового websocket выбирается прокси с минимальной нагрузкой.

После создания соединения счетчик увеличивается.

После закрытия уменьшается.

# Принципы проекта

## Один компонент — одна ответственность

REST не занимается websocket.

WebSocket не занимается REST.

Engine не занимается парсингом.

ProxyManager не занимается биржами.

---

## Максимальная инкапсуляция

Внутреннее устройство биржи не должно быть известно другим пакетам.

Engine не должен знать:

* сколько websocket открыто;
* какие прокси используются;
* как устроен JSON;
* какие URL используются.

---

## Минимум интерфейсов

Интерфейс создается только тогда, когда существует несколько реализаций.

На текущем этапе достаточно:

```
Exchange
```

Возможно позже:

```
ProxyProvider
```

Не создавать интерфейсы "на будущее".

# Критерии успешной архитектуры

Архитектура считается удачной, если:

* новую биржу можно добавить созданием новой папки в `internal/exchange`;
* `Engine` не изменяется при добавлении новых бирж;
* вся логика конкретной биржи находится только внутри её пакета;
* REST, WebSocket, прокси и планировщик независимы друг от друга;
* система без изменений архитектуры способна масштабироваться до тысяч WebSocket-соединений и большого числа источников данных.

---

## Два момента, которые я бы заложил **сразу**, хотя реализовывать можно позже

1. **Событийная модель внутри биржи.** Вместо того чтобы `REST` напрямую говорил `ConnectionManager`, пусть `Sync()` получает результат от REST, вычисляет изменения и уже затем вызывает методы менеджера соединений. Это делает поток данных явным и облегчает тестирование.

2. **Отдельный пакет `internal/core/httpclient`** (или `transport/http` внутри `core`), где будет общая настройка HTTP-клиентов: таймауты, User-Agent, TLS, retry, компрессия и т.д. Тогда каждая биржа будет использовать общий фундамент, а не создавать свои `http.Client` с нуля. Это особенно пригодится, когда источников станет много.
